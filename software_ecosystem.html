0Overview: three languages, one ecosystem

Research software and industry software are built from the same three layers: a fast compiled core, an array layer, and a high-level language that glues them together. Python, C++ and Fortran each own one part of that stack. This note maps the whole ecosystem, from the core language features to the tools that run on supercomputers, with tested examples and links to the best free resources.

Part I Python

1Python: the language core

Fluency with the core language matters more than knowledge of any library: the data model, built-in containers, iteration, functions, classes and typing. These are the building blocks of everything else.

1.1 Everything is an object; names are references

A Python variable is a name bound to an object, not a box holding a value. b = a makes a second name for the same list; it does not copy it. Objects are either mutable (list, dict, set, most user classes) or immutable (int, float, str, tuple, frozenset). Only immutable (hashable) objects can be dictionary keys or set members.

a = [1, 2, 3]
b = a            # same object
b.append(4)
print(a)         # [1, 2, 3, 4]
print(a is b)    # True: identity;  a == b compares values
c = a.copy()     # shallow copy; copy.deepcopy for nested structures

1.3 A worked example: modern Python in thirty lines

Dataclasses, properties, a generator, comprehensions, Counter/defaultdict, structural pattern matching (3.10+) and f-string debugging (3.8+):

p01_core.py
from dataclasses import dataclass, field
from collections import Counter, defaultdict
from typing import Iterator

@dataclass(order=True)
class Star:
    mass: float                       # solar masses
    name: str = field(compare=False)

    @property
    def luminosity(self) -> float:    # rough main-sequence scaling L ~ M^3.5
        return self.mass ** 3.5

def stream(path_lines: list[str]) -> Iterator[Star]:
    """Generator: parse lines lazily, skipping comments."""
    for line in path_lines:
        if line.startswith("#"):
            continue
        name, m = line.split(",")
        yield Star(float(m), name.strip())

lines = ["# name, mass", "Sun, 1.0", "Sirius A, 2.06", "Proxima, 0.12", "Vega, 2.14"]
stars = sorted(stream(lines), reverse=True)            # order=True: sort by mass
print([s.name for s in stars])
print({s.name: round(s.luminosity, 2) for s in stars})  # dict comprehension
by_class = defaultdict(list)
for s in stars:
    by_class["massive" if s.mass > 1.5 else "light"].append(s.name)
print(dict(by_class))
print(Counter("mississippi").most_common(2))
match stars[0]:                                         # structural pattern matching (3.10+)
    case Star(mass=m, name=n) if m > 2:
        print(f"{n} is heavy: {m=}")                    # f-string '=' debugging (3.8+)

1.4 Functions

  • Arguments: positional, keyword, defaults, *args (extra positional, a tuple), **kwargs (extra keyword, a dict), keyword-only after *, positional-only before /.
  • The mutable-default trap: def f(x, items=[]) shares one list across all calls, because defaults are evaluated once. Use items=None.
  • First-class functions and closures: functions can be passed around and can capture variables. This is what makes decorators work.
  • Scope (LEGB): Local, Enclosing, Global, Built-in; nonlocal and global rebind outer names.

1.5 Iteration: iterators, generators, comprehensions

Anything usable in a for loop is an iterable. A generator (a function with yield, or a generator expression (f(x) for x in data)) produces values lazily, so memory stays constant however large the stream. This matters for files and data streams larger than RAM. The standard library module itertools (chain, islice, groupby, product, accumulate, batched in 3.12+) is worth knowing well.

1.6 Classes and the data model

Classes bundle state with behaviour. The data model lets your objects plug into the language: __repr__, __eq__ and __hash__, __len__, __iter__, __getitem__, __enter__/__exit__ (context managers), __call__. Know @property, @classmethod (alternative constructors), @staticmethod, inheritance with super(), and the standard advice to prefer composition over inheritance. Abstract base classes (abc.ABC) and typing.Protocol (structural, "duck" typing that a type checker can verify) define interfaces.

1.7 Errors and resources

Raise specific exceptions (ValueError, TypeError, KeyError) or your own subclasses, and catch only what you can handle. Use try/finally or, better, a with block for anything that must be released. Since 3.11, ExceptionGroup and except* handle several errors at once (useful in concurrent code), and add_note() attaches context to an exception.

1.8 Type hints

Type hints (def f(x: float, n: int = 3) -> list[float]) are not checked at run time, but tools (mypy, pyright) check them statically and editors use them for completion. Modern syntax: list[int] (3.9+), int | None (3.10+), generic functions def first[T](xs: list[T]) -> T (3.12+). In industry codebases, typed code is the norm; in research code it is becoming common.

2Environments, packaging and reproducibility

"It works on my machine" is the most common failure in research software. Environments and packaging are how code becomes something others can install and run. This is exactly the issue that a fresh install on a collaborator's machine exposes.

2.1 Why environments exist

Each project needs its own versions of its dependencies. An environment is an isolated set of installed packages plus an interpreter. Never install project packages into the system Python.

2.4 Reproducibility checklist for a research code

  1. No absolute paths to your own machine (/Users/you/...). Use paths relative to the package (importlib.resources, pathlib.Path(__file__).parent) or configuration and environment variables, with clear errors when something is missing.
  2. Declare every dependency in pyproject.toml; pin exact versions in a lock file (uv.lock, pixi.lock, conda-lock) for reproducing papers.
  3. Separate environments for conflicting stacks (for example PyTorch and JAX with different CUDA builds).
  4. Test from a fresh clone on a clean machine. Continuous integration (Chapter 6) does this on every push.
  5. Fix the random seeds and record versions in outputs.
  6. Licence, README, citation file (CITATION.cff), and a Zenodo DOI for the release used in a paper.

3The scientific stack: NumPy, SciPy, pandas, Polars and friends

NumPy's array is the common currency of scientific Python. Thinking in whole arrays rather than loops is the single most important skill, because it moves the work into compiled code.

3.1 NumPy: vectorisation and broadcasting

A NumPy array is a block of typed memory plus a shape and strides. Operations on whole arrays run in C, often calling optimised BLAS. Broadcasting stretches dimensions of size 1 so that arrays of different shapes combine without copying. The example computes all pairwise distances between particles three ways:

p02_numpy.py
import time
import numpy as np

rng = np.random.default_rng(42)          # modern Generator API (not np.random.seed)
x = rng.normal(size=(2000, 3))           # 2000 particles in 3D

def pairwise_loop(x):
    n = len(x); d = np.empty((n, n))
    for i in range(n):
        for j in range(n):
            d[i, j] = np.sqrt(((x[i] - x[j]) ** 2).sum())
    return d

def pairwise_broadcast(x):
    diff = x[:, None, :] - x[None, :, :]  # (n,1,3) - (1,n,3) -> (n,n,3)
    return np.sqrt((diff ** 2).sum(-1))

def pairwise_gram(x):                     # |a-b|^2 = |a|^2 + |b|^2 - 2 a.b  (BLAS matmul)
    sq = (x ** 2).sum(1)
    return np.sqrt(np.maximum(sq[:, None] + sq[None, :] - 2 * x @ x.T, 0))

small = x[:300]
t = time.perf_counter(); a = pairwise_loop(small); t_loop = time.perf_counter() - t
t = time.perf_counter(); b = pairwise_broadcast(small); t_b = time.perf_counter() - t
print(f"300 particles: loops {t_loop*1e3:.0f} ms, broadcasting {t_b*1e3:.1f} ms, same: {np.allclose(a, b)}")
t = time.perf_counter(); c = pairwise_gram(x); t_g = time.perf_counter() - t
print(f"2000 particles via matrix product: {t_g*1e3:.0f} ms, max error {abs(c - pairwise_broadcast(x)).max():.1e}")
# einsum: the same contraction written as index notation
print(np.allclose(np.einsum("ik,jk->ij", x, x), x @ x.T))
output
300 particles: loops 114 ms, broadcasting 3.6 ms, same: True
2000 particles via matrix product: 29 ms, max error 6.0e-08
True

Broadcasting is about 30 times faster than the double loop. The matrix-product form uses the identity |a−b|² = |a|² + |b|² − 2a·b to turn the problem into one BLAS call; it is fastest at scale, at the price of a little round-off (6×10−8 here). Knowing this trade-off is a mark of numerical maturity.

  • Views vs copies: slicing gives a view (shared memory); fancy indexing and boolean masks give copies.
  • Random numbers: use rng = np.random.default_rng(seed), not the legacy np.random.seed.
  • dtypes: float32 halves memory and is standard on GPUs; float64 is the scientific default.
  • NumPy 2.0 (2024) cleaned up the API and changed type-promotion rules (NEP 50); old code may need small fixes.

3.2 SciPy: the numerical library

Integration of ODEs, optimisation, linear algebra (dense and sparse), FFTs, special functions, interpolation, signal processing, statistics and spatial algorithms (KD-trees). Two classics:

p08_scipy.py
import numpy as np
from scipy.integrate import solve_ivp
from scipy.optimize import curve_fit

# 1) a stiff ODE (Robertson chemical kinetics): implicit solver needed
def robertson(t, y):
    a, b, c = y
    return [-0.04 * a + 1e4 * b * c, 0.04 * a - 1e4 * b * c - 3e7 * b * b, 3e7 * b * b]

for method in ["RK45", "Radau"]:
    sol = solve_ivp(robertson, (0, 40), [1, 0, 0], method=method, rtol=1e-6, atol=1e-10)
    print(f"{method:5s}: {sol.nfev:7d} function evaluations, mass conserved to {abs(sol.y[:, -1].sum() - 1):.1e}")

# 2) non-linear least squares with uncertainties
rng = np.random.default_rng(3)
t = np.linspace(0, 6, 200)
y = 1.0 * np.exp(-0.25 * t) * np.cos(3.0 * t) + rng.normal(0, 0.05, t.size)
f = lambda t, A, g, w: A * np.exp(-g * t) * np.cos(w * t)
p, C = curve_fit(f, t, y, p0=[0.9, 0.3, 3.05], sigma=np.full(t.size, 0.05), absolute_sigma=True)
print("A, gamma, omega =", np.round(p, 3), "+/-", np.round(np.sqrt(np.diag(C)), 3))
output
RK45 :  242066 function evaluations, mass conserved to 2.4e-15
Radau:     647 function evaluations, mass conserved to 1.1e-16
A, gamma, omega = [0.995 0.254 3.003] +/- [0.013 0.006 0.004]

On a stiff problem an explicit solver (RK45) needs hundreds of thousands of evaluations, while an implicit one (Radau) needs a few hundred. curve_fit with absolute_sigma=True returns parameter uncertainties that are correct for known measurement errors.

3.3 Data frames: pandas, Polars and DuckDB

pandas is the standard tool for tabular data, and almost every data-science team uses it. Polars (Rust; 1.0 in 2024) is a newer, much faster data-frame library with a lazy, query-optimised expression API and multithreading. DuckDB is an in-process SQL database that queries data frames, CSV and Parquet files directly. The same monthly-growth query in all three:

p03_frames.py
import numpy as np
import pandas as pd
import polars as pl
import duckdb

rng = np.random.default_rng(0)
n = 100_000
df = pd.DataFrame({
    "date": pd.Timestamp("2026-01-01") + pd.to_timedelta(rng.integers(0, 180, n), unit="D"),
    "site": rng.choice(["Culham", "Sunbury", "Reading"], n),
    "power_kw": rng.gamma(4.0, 25.0, n),
})

# pandas: monthly mean per site, then month-on-month change
m = (df.assign(month=df["date"].dt.to_period("M"))
       .groupby(["site", "month"], as_index=False)["power_kw"].mean())
m["mom_pct"] = m.groupby("site")["power_kw"].pct_change().mul(100).round(2)
print(m.head(3).to_string(index=False))

# polars: the same query, expression API (lazy -> optimised plan, multithreaded)
p = (pl.from_pandas(df).lazy()
       .with_columns(pl.col("date").dt.truncate("1mo").alias("month"))
       .group_by("site", "month").agg(pl.col("power_kw").mean())
       .sort("site", "month")
       .with_columns((pl.col("power_kw").pct_change().over("site") * 100).round(2).alias("mom_pct"))
       .collect())
print(p.head(3))

# DuckDB: plain SQL directly on the pandas DataFrame in memory (window function)
q = duckdb.sql("""
    SELECT site, date_trunc('month', date) AS month, avg(power_kw) AS power_kw,
           round(100 * (avg(power_kw) / lag(avg(power_kw)) OVER (PARTITION BY site ORDER BY date_trunc('month', date)) - 1), 2) AS mom_pct
    FROM df GROUP BY site, month ORDER BY site, month LIMIT 3
""").df()
print(q.to_string(index=False))

4Machine learning and AI: scikit-learn, PyTorch, JAX

Three libraries cover most ML work: scikit-learn for classical models on tables, PyTorch for deep learning (dominant in industry and research), and JAX for differentiable scientific computing. They share one idea: automatic differentiation plus optimisation.

4.1 scikit-learn: classical ML, done properly

The consistent fit/predict/transform API, Pipelines that keep preprocessing inside cross-validation (preventing leakage), and honest evaluation. The example models rare equipment failures, a common industrial problem:

p04_sklearn.py
import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import average_precision_score
from sklearn.model_selection import StratifiedKFold, cross_val_score
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

# synthetic "pump failure" data: rare positives (about 10%)
rng = np.random.default_rng(1)
n = 4000
X = pd.DataFrame({
    "vibration_rms": rng.gamma(2, 1, n),
    "temp_c": rng.normal(60, 8, n),
    "age_years": rng.uniform(0, 20, n),
    "site": rng.choice(["A", "B", "C"], n),
})
logit = -6 + 0.9 * X.vibration_rms + 0.05 * (X.temp_c - 60) + 0.1 * X.age_years + 0.8 * (X.site == "C")
y = rng.random(n) < 1 / (1 + np.exp(-logit))
print(f"positive rate: {y.mean():.3f}")

pre = ColumnTransformer([
    ("num", StandardScaler(), ["vibration_rms", "temp_c", "age_years"]),
    ("cat", OneHotEncoder(handle_unknown="ignore"), ["site"]),
])
models = {
    "logistic": make_pipeline(pre, LogisticRegression(max_iter=1000, class_weight="balanced")),
    "boosting": make_pipeline(pre, HistGradientBoostingClassifier(max_depth=3, learning_rate=0.05)),
}
cv = StratifiedKFold(5, shuffle=True, random_state=0)   # preprocessing is re-fitted inside each fold: no leakage
for name, model in models.items():
    ap = cross_val_score(model, X, y, cv=cv, scoring="average_precision")
    print(f"{name:9s} PR-AUC = {ap.mean():.3f} +/- {ap.std():.3f}   (a random guess scores {y.mean():.3f})")
output
positive rate: 0.099
logistic  PR-AUC = 0.505 +/- 0.059   (a random guess scores 0.099)
boosting  PR-AUC = 0.485 +/- 0.047   (a random guess scores 0.099)

Points to note: the preprocessing sits inside the pipeline, so it is re-fitted on each training fold; the metric is precision–recall AUC, not accuracy, because failures are rare; and the simple logistic model matches gradient boosting here, because the data were generated by a logistic model. Always compare against a simple baseline. On real tabular data, gradient boosting (scikit-learn's HistGradientBoosting, XGBoost, LightGBM, CatBoost) is usually the strongest method.

4.2 PyTorch: deep learning

Tensors (like NumPy arrays, on CPU or GPU), autograd (reverse-mode automatic differentiation), nn.Module for models, optimisers, DataLoader. PyTorch 2.x added torch.compile, which compiles models for speed. A minimal training loop learning a physics function (the pendulum period at large amplitude, with the exact answer from the arithmetic–geometric mean):

p06_torch.py
import torch
from torch import nn

torch.manual_seed(0)
# learn the 1D pendulum period T(theta0)/T0 from samples (a smooth physics function)
theta0 = torch.rand(2000, 1) * 2.5                       # amplitude in radians
k = torch.sin(theta0 / 2)
# exact ratio via the arithmetic-geometric mean: T/T0 = 1 / AGM(1, sqrt(1-k^2))
a, b = torch.ones_like(k), torch.sqrt(1 - k**2)
for _ in range(8):
    a, b = (a + b) / 2, torch.sqrt(a * b)
ratio = 1 / a

net = nn.Sequential(nn.Linear(1, 32), nn.Tanh(), nn.Linear(32, 32), nn.Tanh(), nn.Linear(32, 1))
opt = torch.optim.Adam(net.parameters(), lr=3e-3)
train, test = slice(0, 1600), slice(1600, 2000)
for epoch in range(4000):
    opt.zero_grad()
    loss = nn.functional.mse_loss(net(theta0[train]), ratio[train])
    loss.backward()                                      # autograd computes all gradients
    opt.step()
with torch.no_grad():
    err = (net(theta0[test]) - ratio[test]).abs().max().item()
print(f"train MSE {loss.item():.2e}, worst test error {err:.1e} (ratio ranges 1 to {ratio.max().item():.2f})")
output
train MSE 3.56e-06, worst test error 6.6e-03 (ratio ranges 1 to 1.64)

4.3 JAX: NumPy with gradients, compilation and vectorisation

JAX (Google) is jax.numpy plus composable function transformations: grad (derivatives), jit (compile with XLA for CPU, GPU or TPU), vmap (vectorise any function over a batch dimension) and pmap/sharding (multiple devices). It is functional: no in-place updates, explicit random keys. It has become popular in physics (differentiable simulators, cosmology emulators, HMC with NumPyro and BlackJAX), because exact gradients of complicated physical models come for free:

p05_jax.py
import jax
import jax.numpy as jnp
import numpy as np

jax.config.update("jax_enable_x64", True)

# data: damped oscillator y = A exp(-g t) cos(w t) + noise
rng = np.random.default_rng(0)
t = jnp.linspace(0, 6, 400)
y = 1.0 * jnp.exp(-0.25 * t) * jnp.cos(3.0 * t) + 0.05 * rng.normal(size=t.size)

def model(theta, t):
    A, g, w = theta
    return A * jnp.exp(-g * t) * jnp.cos(w * t)

def chi2(theta):
    return jnp.sum((y - model(theta, t)) ** 2) / 0.05**2

def residuals(theta):
    return (y - model(theta, t)) / 0.05

jac = jax.jit(jax.jacfwd(residuals))     # exact Jacobian by automatic differentiation, compiled by XLA
hess = jax.jit(jax.hessian(chi2))        # exact Hessian of chi^2 -> Fisher matrix = Hessian / 2

theta = jnp.array([0.9, 0.3, 3.05])
for _ in range(10):                      # Gauss-Newton: solve (J^T J) step = -J^T r
    J, r = jac(theta), residuals(theta)
    theta = theta - jnp.linalg.solve(J.T @ J, J.T @ r)
cov = jnp.linalg.inv(hess(theta) / 2)
print("best fit  A, gamma, omega =", np.round(np.asarray(theta), 4))
print("1-sigma errors            =", np.round(np.sqrt(np.diag(np.asarray(cov))), 4))

# vmap: evaluate chi2 for 10,000 parameter vectors at once, no Python loop
thetas = jnp.stack([jnp.linspace(0.5, 1.5, 10_000), jnp.full(10_000, 0.25), jnp.full(10_000, 3.0)], axis=1)
scan = jax.vmap(chi2)(thetas)
print("best A on the grid        =", float(thetas[jnp.argmin(scan), 0]).__round__(4), "| device:", jax.devices()[0].platform)

"Python is slow" is only true of Python loops. The craft is to measure first, then move the hot loop into compiled code, across cores, across nodes, or onto a GPU.

5.1 Measure first

  • cProfile + snakeviz for function-level profiles; line_profiler for line by line; py-spy and Scalene for sampling profiles of running programs (Scalene separates Python, native and memory time). Python 3.15 adds a built-in sampling profiler.
  • Memory: memray, tracemalloc.

5.2 The ladder of speed-ups

  1. Better algorithm (O(n log n) instead of O(n²); a KD-tree instead of all pairs). Usually the biggest win.
  2. Vectorise with NumPy (Chapter 3).
  3. Compile the loop with Numba: a decorator that compiles numerical Python to machine code with LLVM, including threads with prange:
    p07_numba.py
    import time
import numpy as np
from numba import njit, prange

def energy_python(x, m, eps):
    n, e = len(m), 0.0
    for i in range(n):
        for j in range(i + 1, n):
            r = np.sqrt(((x[i] - x[j]) ** 2).sum() + eps * eps)
            e -= m[i] * m[j] / r
    return e

@njit(parallel=True, fastmath=False, cache=True)
def energy_numba(x, m, eps):
    n, e = len(m), 0.0
    for i in prange(n):                      # parallel over i (OpenMP-like threads)
        ei = 0.0
        for j in range(i + 1, n):
            dx = x[i, 0] - x[j, 0]; dy = x[i, 1] - x[j, 1]; dz = x[i, 2] - x[j, 2]
            ei -= m[i] * m[j] / np.sqrt(dx * dx + dy * dy + dz * dz + eps * eps)
        e += ei                              # numba turns this into a reduction
    return e

rng = np.random.default_rng(0)

5.3 Concurrency: threads, processes, async, and the GIL

In standard CPython the Global Interpreter Lock (GIL) lets only one thread run Python bytecode at a time. So:

WorkloadUse
Waiting on I/O (web requests, files, databases)threading, concurrent.futures.ThreadPoolExecutor, or asyncio

import time
from concurrent.futures import ProcessPoolExecutor
import numpy as np

def darts(seed, n=4_000_000):
    rng = np.random.default_rng(seed)
    x, y = rng.random(n), rng.random(n)
    return int(np.count_nonzero(x * x + y * y <= 1.0))

if __name__ == "__main__":                       # required for process pools on macOS/Windows
    seeds = range(8)
    t = time.perf_counter(); serial = sum(map(darts, seeds)); t1 = time.perf_counter() - t
    t = time.perf_counter()
    with ProcessPoolExecutor() as pool:          # one Python process per core: sidesteps the GIL
        parallel = sum(pool.map(darts, seeds))
    t2 = time.perf_counter() - t
    print(f"pi ~ {4 * parallel / (8 * 4_000_000):.5f}; serial {t1:.2f} s, process pool {t2:.2f} s, same: {serial == parallel}")

src/orbits/kepler.py
import numpy as np
from numpy.typing import ArrayLike, NDArray


def solve_kepler(
    M: ArrayLike, e: float, tol: float = 1e-13, maxiter: int = 50
) -> NDArray[np.float64]:
    """Solve Kepler's equation E - e sin E = M for the eccentric anomaly E (Newton's method).

    Vectorised over M. Raises ValueError for e outside [0, 1).
    """
    if not 0 <= e < 1:
        raise ValueError(f"eccentricity must be in [0, 1), got {e}")
    M = np.asarray(M, dtype=float)
    E = np.where(e > 0.8, np.pi, M)              # robust starting guess for high e
    for _ in range(maxiter):
        dE = (E - e * np.sin(E) - M) / (1 - e * np.cos(E))
        E = E - dE
        if np.all(np.abs(dE) < tol):
            return E
    raise RuntimeError("Kepler solver did not converge")

9Modern C++: the essential core

"Modern C++" means C++11 and later: code that manages memory through ownership rather than raw new and delete, uses the standard library, and is both safe and fast. C++17 is today's industry baseline; C++20 is increasingly common.

9.1 The ideas behind the questions

RAII
"Resource acquisition is initialisation": an object acquires a resource (memory, file, lock) in its constructor and releases it in its destructor, so clean-up happens automatically, even when exceptions are thrown. This is the central idea of C++.
Ownership
std::unique_ptr (one owner; zero overhead), std::shared_ptr (shared, reference-counted), raw pointers and references only to observe. Prefer values and containers; create objects with std::make_unique.
Value semantics and moves
Copying a large object is expensive; move semantics (C++11) transfers its internals instead. std::move marks an object as movable from.
Rule of zero / five
If a class only holds well-behaved members (vectors, smart pointers), write none of the copy, move or destructor functions (rule of zero). If it manages a raw resource, define all five.
Stack vs heap
Local objects live on the stack and die at the end of scope; dynamic allocation is on the heap and needs an owner.
const correctness
const parameters, member functions that do not modify the object, and const& for large inputs.
Polymorphism
Run time: virtual functions through a base pointer, with a virtual destructor. Compile time: templates (zero run-time cost).
Undefined behaviour
Out-of-bounds access, use after free, signed overflow and data races are not errors the language catches. They may appear to work. Sanitizers (Chapters 10 and 15) find them.

9.2 A worked example: modern C++ in one program

class Field {
public:
    explicit Field(std::size_t n, double v = 0.0) : data_(n, v) {}
    double& operator[](std::size_t i) { return data_[i]; }
    std::span<const double> view() const { return data_; }   // C++20: non-owning view
    std::size_t size() const { return data_.size(); }
private:
    std::vector<double> data_;
};

// Runtime polymorphism: virtual interface + virtual destructor.
struct Potential {
    virtual ~Potential() = default;
    virtual double operator()(double r) const = 0;
};
struct Plummer final : Potential {
    double a;
    explicit Plummer(double a_) : a(a_) {}
    double operator()(double r) const override { return -1.0 / std::sqrt(r * r + a * a); }
};

// C++17 std::optional: a result that may be absent, instead of a magic value like -1.
std::optional<double> safe_sqrt(double x) {
    if (x < 0) return std::nullopt;
    return std::sqrt(x);
}

double mean(std::span<const double> xs) {                        // works for vector, array, C array
    return std::accumulate(xs.begin(), xs.end(), 0.0) / static_cast<double>(xs.size());
}

int main() {
    // smart pointers: unique ownership, freed automatically
    std::unique_ptr<Potential> phi = std::make_unique<Plummer>(0.1);
    std::cout << "phi(1) = " << (*phi)(1.0) << '\n';

    // move semantics: steal the buffer instead of copying a million doubles
    Field f(1'000'000, 1.0);
    Field g = std::move(f);
    std::cout << "moved field size " << g.size() << ", mean " << mean(g.view()) << '\n';

    // lambdas + algorithms
    std::vector<double> r{0.5, 2.0, 0.1, 1.5};
    std::sort(r.begin(), r.end(), [](double a, double b) { return a > b; });
    std::cout << "sorted descending: ";
    for (double x : r) std::cout << x << ' ';
    std::cout << '\n';

    // C++17 structured bindings over a map
    std::map<std::string, double> masses{{"Sun", 1.0}, {"Vega", 2.14}};
    for (const auto& [name, m] : masses) std::cout << name << " -> " << m << '\n';

    // C++20 ranges: lazy filter + transform pipeline
    auto squares_of_even = std::views::iota(1, 11)
                         | std::views::filter([](int i) { return i % 2 == 0; })
                         | std::views::transform([](int i) { return i * i; });
    std::cout << "squares of even numbers: ";
    for (int s : squares_of_even) std::cout << s << ' ';
    std::cout << '\n';

    if (auto v = safe_sqrt(-4.0); !v) std::cout << "sqrt(-4): no real value\n";
    std::cout << "sqrt(9) = " << safe_sqrt(9.0).value() << '\n';
}

    T s = 0;
    for (T v : x) s += v * v;
    return std::sqrt(s / static_cast<T>(x.size()));
}

11C++ in HPC and science: OpenMP, MPI, GPUs, and Python bindings

Most large new scientific and engineering codes are written in C++, with parallelism at three levels: threads within a node, MPI across nodes, and GPUs. And almost all of them now have a Python interface.

11.1 Threads: OpenMP

One pragma parallelises a loop; reduction combines per-thread partial sums safely. Pairwise potential energy of 20,000 bodies (2×108 pairs):

omp_sum.cpp
// omp_sum.cpp -- OpenMP: parallel reduction for the gravitational potential energy of N bodies.
// Build: g++ -std=c++17 -O3 -fopenmp omp_sum.cpp -o omp_sum && OMP_NUM_THREADS=4 ./omp_sum
// macOS (Apple clang has no OpenMP): brew install libomp, or use g++-14 from Homebrew.
#include <chrono>
#include <cmath>
#include <iostream>
#include <random>
#include <vector>
#include <omp.h>

int main() {
    const int n = 20000;
    std::mt19937_64 rng(42);
    std::normal_distribution<double> N(0.0, 1.0);
    std::vector<double> x(n), y(n), z(n);
    for (int i = 0; i < n; ++i) { x[i] = N(rng); y[i] = N(rng); z[i] = N(rng); }

    auto t0 = std::chrono::steady_clock::now();
    double energy = 0.0;
    #pragma omp parallel for reduction(+ : energy) schedule(dynamic, 64)
    for (int i = 0; i < n; ++i)
        for (int j = i + 1; j < n; ++j) {
            const double dx = x[i] - x[j], dy = y[i] - y[j], dz = z[i] - z[j];
            energy -= 1.0 / std::sqrt(dx * dx + dy * dy + dz * dz + 1e-4);
        }
    const double secs = std::chrono::duration<double>(std::chrono::steady_clock::now() - t0).count();
    std::cout << "threads " << omp_get_max_threads() << ", E = " << energy << ", "
              << secs << " s for " << (double)n * (n - 1) / 2 << " pairs\n";
}
output
threads 1, E = -1.12826e+08, 0.269067 s for 1.9999e+08 pairs
threads 2, E = -1.12826e+08, 0.13705 s for 1.9999e+08 pairs

Two threads halve the time, and the result is identical. schedule(dynamic) balances the triangular loop, where early rows have more work. OpenMP 4.5+ can also offload loops to GPUs (#pragma omp target).

11.2 Processes across nodes: MPI

// fastkepler.cpp -- expose a C++ function to Python with pybind11 (zero-copy NumPy arrays).
#include <cmath>
#include <stdexcept>
#include <pybind11/numpy.h>
#include <pybind11/pybind11.h>
namespace py = pybind11;

py::array_t<double> solve_kepler(py::array_t<double, py::array::c_style | py::array::forcecast> M, double e) {
    if (e < 0.0 || e >= 1.0) throw std::invalid_argument("eccentricity must be in [0, 1)");
    auto in = M.unchecked<1>();
    py::array_t<double> E(in.shape(0));
    auto out = E.mutable_unchecked<1>();
    {
        py::gil_scoped_release release;            // pure C++ below: let other Python threads run
        for (py::ssize_t i = 0; i < in.shape(0); ++i) {
            double x = e > 0.8 ? M_PI : in(i);
            for (int it = 0; it < 50; ++it) {
                const double dx = (x - e * std::sin(x) - in(i)) / (1.0 - e * std::cos(x));
                x -= dx;
                if (std::abs(dx) < 1e-13) break;
            }
            out(i) = x;
        }
    }
    return E;
}

13.2 A worked example: a modern Fortran program

A periodic 1D diffusion solver using a module, a derived type with an allocatable component, an elemental function with an array constructor, do concurrent and whole-array arithmetic:

heat.f90
! heat.f90 -- modern Fortran (2008+): modules, derived types, array syntax, pure/elemental, do concurrent.
! Build: gfortran -O3 -std=f2018 -Wall heat.f90 -o heat && ./heat
module grid_mod
  use, intrinsic :: iso_fortran_env, only: dp => real64
  implicit none
  private
  public :: dp, grid_t, init_gaussian, step, total_heat

  type :: grid_t
     integer :: n
     real(dp) :: dx, kappa
     real(dp), allocatable :: u(:)            ! allocatable: freed automatically (RAII-like)
  end type grid_t

contains

  pure elemental real(dp) function gaussian(x, sigma)
    real(dp), intent(in) :: x, sigma
    gaussian = exp(-0.5_dp * (x / sigma)**2)
  end function gaussian

  subroutine init_gaussian(g, n, length, kappa)
    type(grid_t), intent(out) :: g
    integer, intent(in) :: n
    real(dp), intent(in) :: length, kappa
    integer :: i
    g%n = n; g%dx = length / n; g%kappa = kappa
    allocate(g%u(n))
    g%u = gaussian([(real(i, dp) * g%dx - 0.5_dp * length, i = 1, n)], 0.05_dp * length)  ! array constructor + elemental
  end subroutine init_gaussian

  subroutine step(g, dt)                     ! explicit diffusion step, periodic boundaries
    type(grid_t), intent(inout) :: g
    real(dp), intent(in) :: dt
    real(dp) :: lap(g%n)
    integer :: i
    do concurrent (i = 1:g%n)                ! iterations independent: compiler may vectorise/parallelise
       lap(i) = g%u(modulo(i - 2, g%n) + 1) - 2.0_dp * g%u(i) + g%u(modulo(i, g%n) + 1)
    end do
    g%u = g%u + g%kappa * dt / g%dx**2 * lap  ! whole-array arithmetic
  end subroutine step

  pure real(dp) function total_heat(g)
    type(grid_t), intent(in) :: g
    total_heat = sum(g%u) * g%dx
  end function total_heat

end module grid_mod

program heat
  use grid_mod
  implicit none
  type(grid_t) :: g
  real(dp) :: dt, q0
  integer :: it
  call init_gaussian(g, 400, 1.0_dp, 1.0e-3_dp)
  dt = 0.4_dp * g%dx**2 / g%kappa             ! stability: dt <= dx^2 / (2 kappa)
  q0 = total_heat(g)
  do it = 1, 5000
     call step(g, dt)
  end do
  print '(a, es10.3, a, f8.5)', 'relative heat change ', abs(total_heat(g) - q0) / q0, &
        ';  peak now ', maxval(g%u)
end program heat
output
relative heat change  4.429E-16;  peak now  0.30150

Heat is conserved to round-off (4×10−16), which is the check a physicist would write as a test. Notes: implicit none always; kinds from iso_fortran_env (real64) instead of real*8; intent on every argument; modules instead of COMMON blocks.

13.3 Interoperability: Fortran with C, C++ and Python

bind(C) gives a Fortran routine a C name and calling convention, so C, C++, Rust and Python can call it. A trapezium-rule integrator built as a shared library and called from Python with ctypes, reading NumPy's memory directly:

cfun.f90
! cfun.f90 -- Fortran callable from C, C++ and Python through iso_c_binding (Fortran 2003).
! Build a shared library: gfortran -O3 -shared -fPIC cfun.f90 -o libcfun.so   (.dylib on macOS)
module cfun
  use, intrinsic :: iso_c_binding, only: c_double, c_int
  implicit none
contains
  subroutine trapz(n, x, y, result) bind(C, name="trapz")
    integer(c_int), value, intent(in) :: n
    real(c_double), intent(in) :: x(n), y(n)
    real(c_double), intent(out) :: result
    result = 0.5_c_double * sum((x(2:n) - x(1:n-1)) * (y(2:n) + y(1:n-1)))
  end subroutine trapz
end module cfun
call_fortran.py

14.4 Modernising a legacy code: the playbook

A frequent real-world task :

  1. Put it under version control and build it reproducibly (CMake or fpm), with all compiler warnings on.
  2. Write regression tests first: capture current outputs on reference inputs so that every later change can be checked.
  3. Convert to free form, add implicit none, replace COMMON blocks with modules and GOTO with structured loops, add intent (tools such as fprettify, findent and fpt help).
  4. Modularise into modules and derived types; separate physics from I/O.
  5. Add a Python interface (f2py or bind(C)) so that new users can drive the code from Python and test it with pytest.
  6. Parallelise or port to GPUs with OpenMP or OpenACC, or with a tool like PSyclone; profile at each step.
  7. Decide case by case whether to keep Fortran, wrap it, or rewrite parts in C++ or Python. A full rewrite is rarely the best first move.

15Debugging Python, C++ and Fortran: on a Mac, a workstation and a cluster

Debugging is a method, not a tool: reproduce the bug reliably, make it small, form a hypothesis, test it, and add a test so it never comes back. The tools below make each step faster. The examples show bugs that run without complaint and give wrong answers, which are the dangerous kind in scientific code.

15.1 The method

  1. Reproduce with the smallest input and a fixed random seed.
  2. Make failures loud: turn warnings into errors, check for NaNs, enable bounds checking and sanitizers.
  3. Localise: read the traceback from the bottom; use a debugger to inspect variables where it failed; bisect (comment out halves, or git bisect to find the commit that introduced it).
  4. Fix, then add a regression test that fails without the fix.

  • Interactive jobs: debug on a compute node, not the login node. PBS clusters: qsub -I -l select=1:ncpus=4:mem=16gb -l walltime=01:00:00; Slurm: srun --pty -t 1:00:00 bash. Add ngpus=1 (PBS) or --gpus=1 (Slurm) for a GPU.
  • VS Code Remote-SSH gives a full graphical debugger on the remote machine (connect through the VPN to the login node).
  • OpenMP: run with OMP_NUM_THREADS=1 first: if the bug disappears, suspect a data race, and use ThreadSanitizer.
  • MPI: reproduce with 2 ranks; print the rank in every message; attach gdb to one rank (mpirun -np 2 xterm -e gdb ./prog on a workstation), or use a parallel debugger (Linaro DDT, TotalView) on HPC systems. 16Profiling and performance: CPU and GPU, Mac and Linux

Never optimise by guessing. Profilers show where the time actually goes, which is usually somewhere unexpected. Measure, fix the biggest cost, measure again.

16.1 Timing correctly

  • Time the real workload, after a warm-up (the first call of a JIT-compiled function includes compilation).
  • Repeat and take the best or median (%timeit, python -m timeit); report the hardware and thread count.
  • GPUs (and JAX even on a CPU) run asynchronously: a function returns before the work is done, so naive timing measures almost nothing:
async_timing.py
"""GPU-style asynchronous execution: why naive timing lies (runs on CPU too)."""
import time
import jax
import jax.numpy as jnp

x = jax.random.normal(jax.random.key(0), (3000, 3000))
f = jax.jit(lambda a: (a @ a.T).sum())
f(x).block_until_ready()                      # warm-up: first call includes compilation

t = time.perf_counter(); y = f(x); t_naive = time.perf_counter() - t                 # returns before the work is done
t = time.perf_counter(); y = f(x).block_until_ready(); t_true = time.perf_counter() - t
print(f"naive timing {t_naive*1e3:.2f} ms  vs  with block_until_ready {t_true*1e3:.1f} ms")
# PyTorch on a GPU: call torch.cuda.synchronize() before reading the clock, or use torch.cuda.Event timers.
output
naive timing 2.77 ms  vs  with block_until_ready 302.2 ms

The naive measurement is about 90 times too small. In PyTorch on a GPU, call torch.cuda.synchronize() before reading the clock.

16.2 Profiling Python

cProfile (built in) times every function. A pipeline with a hidden bottleneck:

slow_pipeline.py
"""A small analysis pipeline with a hidden bottleneck, to practise profiling on."""
import numpy as np


def load(n, rng):
    return rng.normal(size=(n, 3))


def pair_counts(x, rmax):
    # O(n^2) Python loop: the bottleneck
    count = 0
    for i in range(len(x)):
        d = np.sqrt(((x[i + 1:] - x[i]) ** 2).sum(axis=1))
        count += int((d < rmax).sum())
    return count


def summary(x):
    return x.mean(axis=0), np.cov(x.T)


def main():
    rng = np.random.default_rng(1)
    x = load(4000, rng)
    mu, cov = summary(x)
    print("pairs closer than 0.5:", pair_counts(x, 0.5))


if __name__ == "__main__":
    main()

"""After profiling: replace the O(n^2) loop with a KD-tree (O(n log n))."""
import time
import numpy as np
from scipy.spatial import cKDTree
from slow_pipeline import pair_counts

x = np.random.default_rng(1).normal(size=(4000, 3))
t = time.perf_counter(); slow = pair_counts(x, 0.5); t_slow = time.perf_counter() - t
t = time.perf_counter(); fast = len(cKDTree(x).query_pairs(0.5)); t_fast = time.perf_counter() - t
print(f"loop: {slow} pairs in {t_slow*1e3:.0f} ms;  KD-tree: {fast} pairs in {t_fast*1e3:.0f} ms;  same: {slow == fast}")

16.3 Profiling compiled code (C++, Fortran, extensions)

Build with optimisation and symbols: -O2 -g (add -fno-omit-frame-pointer for better call stacks). Example: which of two functions dominates?

hotspot.cpp
// hotspot.cpp -- two functions; which one dominates? Profile, don't guess.
#include <cmath>
#include <iostream>
#include <vector>

double potential(const std::vector<double>& x) {          // O(n^2)
    double e = 0.0;
    for (std::size_t i = 0; i < x.size(); ++i)
        for (std::size_t j = i + 1; j < x.size(); ++j)
            e -= 1.0 / std::sqrt((x[i] - x[j]) * (x[i] - x[j]) + 1e-3);
    return e;
}

double kinetic(const std::vector<double>& v) {            // O(n)
    double e = 0.0;
    for (double vi : v) e += 0.5 * vi * vi;
    return e;
}

int main() {
    const std::size_t n = 6000;
    std::vector<double> x(n), v(n);
    for (std::size_t i = 0; i < n; ++i) { x[i] = std::sin(0.37 * i); v[i] = std::cos(0.11 * i); }
    double total = 0.0;
    for (int step = 0; step < 5; ++step) total += kinetic(v) + potential(x);
    std::cout << "total energy " << total << '\n';
}

16.4 Is the code compute-bound or memory-bound?

The roofline model compares a kernel's arithmetic intensity (floating-point operations per byte moved) with the machine's peak compute and memory bandwidth. Most stencil, PIC deposit and sparse codes are memory-bound: speed-ups come from better data layout (structure of arrays, contiguous access, cache blocking), not from fewer operations. VTune, LIKWID, Nsight Compute and Intel Advisor draw rooflines.

16.5 Parallel scaling (OpenMP and MPI)

  • Strong scaling: fixed problem, more cores; expect Amdahl's law to flatten the curve. Weak scaling: problem grows with cores; ideal is constant run time. Always plot both, with efficiency, for a proposal or report.
  • OpenMP: time with OMP_NUM_THREADS = 1, 2, 4, 8…; pin threads (OMP_PROC_BIND=close OMP_PLACES=cores); VTune shows load imbalance and barrier waiting.
  • MPI: Linaro MAP, Score-P with Vampir or Scalasca, TAU, mpiP (lightweight: time in each MPI call), and Darshan for parallel I/O. Look for communication time growing with rank count and for ranks waiting on the slowest one.
  • On a PBS cluster, profile inside the batch job, for example perf record -g -o perf.$PBS_JOBID ./prog, or load the site's profiler module (module avail).

16.7 A profiling checklist

  1. Is the answer still correct? (Tests pass before and after every optimisation.)
  2. Where does the time go? (Profile; do not guess.)
  3. Is there a better algorithm or library call? (Usually the biggest win.)
  4. Is the hot loop vectorised or compiled? (NumPy, Numba, C++/Fortran with -O3 -march=native.)
  5. Is it memory-bound? (Data layout, contiguity, fewer passes over memory.)
  6. Does it scale across cores, nodes or a GPU? (Measure strong and weak scaling.)
  7. Record the result: hardware, versions, timings, so it can be reproduced.

B.3 The classic OpenMP bug, and three correct fixes

Building a histogram, such as counting particles per cell, is where races appear in real codes:

omp_pitfalls.cpp
// omp_pitfalls.cpp -- the classic OpenMP bug (a data race) and three correct fixes.
// Build: g++ -std=c++17 -O2 -fopenmp omp_pitfalls.cpp -o omp_pitfalls && OMP_NUM_THREADS=4 ./omp_pitfalls
#include <cstdio>
#include <vector>
#include <omp.h>

constexpr int NBINS = 16;

void racy(const std::vector<int>& x, long* h) {
    #pragma omp parallel for
    for (std::size_t i = 0; i < x.size(); ++i) h[x[i]] += 1;            // WRONG: unsynchronised update
}
void atomic(const std::vector<int>& x, long* h) {
    #pragma omp parallel for
    for (std::size_t i = 0; i < x.size(); ++i) {
        #pragma omp atomic
        h[x[i]] += 1;                                                    // correct; threads contend
    }
}
void array_reduction(const std::vector<int>& x, long* h) {
    #pragma omp parallel for reduction(+ : h[:NBINS])                    // private copies, summed at the end
    for (std::size_t i = 0; i < x.size(); ++i) h[x[i]] += 1;
}
void private_merge(const std::vector<int>& x, long* h) {
    #pragma omp parallel
    {
        long mine[NBINS] = {};                                           // thread-private histogram
        #pragma omp for nowait
        for (std::size_t i = 0; i < x.size(); ++i) mine[x[i]] += 1;
        #pragma omp critical                                             // one thread at a time, NBINS adds
        for (int b = 0; b < NBINS; ++b) h[b] += mine[b];
    }
}

int main() {
    const int n = 20'000'000;
    std::vector<int> x(n);
    for (int i = 0; i < n; ++i) x[i] = (i * 2654435761u) % NBINS;        // e.g. particle -> cell index
    struct { const char* name; void (*f)(const std::vector<int>&, long*); } variants[] = {
        {"racy (WRONG)", racy}, {"atomic", atomic}, {"array reduction", array_reduction}, {"private + merge", private_merge}};
    std::printf("threads: %d\n", omp_get_max_threads());
    for (auto& v : variants) {
        long h[NBINS] = {};
        const double t0 = omp_get_wtime();
        v.f(x, h);
        const double dt = omp_get_wtime() - t0;
        long total = 0;
        for (long c : h) total += c;
        std::printf("%-17s counted %9ld of %d  (%.3f s)\n", v.name, total, n, dt);
    }
}

The racy loop loses almost 40% of the counts with only two threads, without any error message, and is also slower because the threads fight over the same cache lines. atomic is correct but slow when threads contend; the array reduction and the private-plus-merge pattern are correct and fastest. The same ideas apply to charge deposition in particle-in-cell codes and to mass assignment in N-body codes.

Other OpenMP performance points:

  • False sharing: threads writing to different variables that share one 64-byte cache line slow each other down. Pad per-thread data to cache-line size, or accumulate in thread-local variables.
  • First touch and NUMA: memory is placed near the core that first writes it, so initialise big arrays inside a parallel loop with the same schedule as the compute loops.
  • Amdahl's law: the serial fraction limits the speed-up; parallelise the outer loops and avoid repeatedly starting parallel regions inside tight loops.
  • Check with ThreadSanitizer (-fsanitize=thread) and Intel Inspector or VTune.

B.5 Domain decomposition with halo exchange

The workhorse pattern of grid codes: each rank owns a piece of the domain plus "ghost" cells holding copies of its neighbours' edge values, refreshed every step. A periodic 1D diffusion problem split across ranks:

mpi_heat.cpp
// mpi_heat.cpp -- domain decomposition with halo exchange: 1D diffusion split across MPI ranks.
// Build: mpicxx -std=c++17 -O2 mpi_heat.cpp -o mpi_heat      Run: mpirun -np 4 ./mpi_heat
#include <cmath>
#include <cstdio>
#include <vector>
#include <mpi.h>

int main(int argc, char** argv) {
    MPI_Init(&argc, &argv);
    int rank, size;
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    MPI_Comm_size(MPI_COMM_WORLD, &size);

    const int N = 4000;                              // global grid (periodic)
    const int n = N / size;                          // cells owned by this rank (assume divisible)
    const double dx = 1.0 / N, kappa = 1e-3, dt = 0.4 * dx * dx / kappa;
    std::vector<double> u(n + 2), unew(n + 2);       // u[0] and u[n+1] are ghost (halo) cells
    for (int i = 1; i <= n; ++i) {
        const double x = (rank * n + i - 0.5) * dx - 0.5;
        u[i] = std::exp(-0.5 * (x / 0.05) * (x / 0.05));
    }
    const int left = (rank - 1 + size) % size, right = (rank + 1) % size;

    auto total_heat = [&] {
        double local = 0.0, global = 0.0;
        for (int i = 1; i <= n; ++i) local += u[i] * dx;
        MPI_Allreduce(&local, &global, 1, MPI_DOUBLE, MPI_SUM, MPI_COMM_WORLD);   // every rank gets the sum
        return global;
    };
    const double q0 = total_heat();
    const double t0 = MPI_Wtime();
    for (int step = 0; step < 20000; ++step) {
        // halo exchange: send my edge cells to neighbours, receive theirs into my ghost cells
        MPI_Sendrecv(&u[n], 1, MPI_DOUBLE, right, 0, &u[0],     1, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
        MPI_Sendrecv(&u[1], 1, MPI_DOUBLE, left,  1, &u[n + 1], 1, MPI_DOUBLE, right, 1, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
        for (int i = 1; i <= n; ++i) unew[i] = u[i] + kappa * dt / (dx * dx) * (u[i - 1] - 2 * u[i] + u[i + 1]);
        std::swap(u, unew);
    }
    const double elapsed = MPI_Wtime() - t0, q1 = total_heat();
    double peak_local = 0.0, peak = 0.0;
    for (int i = 1; i <= n; ++i) peak_local = std::max(peak_local, u[i]);
    MPI_Reduce(&peak_local, &peak, 1, MPI_DOUBLE, MPI_MAX, 0, MPI_COMM_WORLD);         // only rank 0 gets it
    if (rank == 0)
        std::printf("ranks %d: heat conserved to %.1e, peak %.5f, %.2f s\n", size, std::abs(q1 - q0) / q0, peak, elapsed);
    MPI_Finalize();
}

B.6 Hybrid MPI + OpenMP

hybrid_pi.cpp
// hybrid_pi.cpp -- MPI between processes + OpenMP threads inside each: the standard HPC pattern.
// Build: mpicxx -std=c++17 -O2 -fopenmp hybrid_pi.cpp -o hybrid_pi
// Run:   OMP_NUM_THREADS=2 mpirun -np 2 ./hybrid_pi      (on a cluster: ranks per node x threads per rank = cores)
#include <cmath>
#include <cstdio>
#include <mpi.h>
#include <omp.h>

int main(int argc, char** argv) {
    int provided;
    MPI_Init_thread(&argc, &argv, MPI_THREAD_FUNNELED, &provided);   // only the main thread calls MPI
    int rank, size;
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    MPI_Comm_size(MPI_COMM_WORLD, &size);

    const long n = 200'000'000;                  // midpoint rule for pi = integral of 4/(1+x^2) on [0,1]
    const long lo = rank * n / size, hi = (rank + 1) * n / size;   // this rank's share of the intervals
    const double h = 1.0 / n;
    double local = 0.0;
    #pragma omp parallel for reduction(+ : local)                   // threads split this rank's share
    for (long i = lo; i < hi; ++i) {
        const double x = (i + 0.5) * h;
        local += 4.0 / (1.0 + x * x);
    }
    double pi = 0.0;
    MPI_Reduce(&local, &pi, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
    if (rank == 0)
        std::printf("%d ranks x %d threads: pi = %.12f (error %.1e)\n",
                    size, omp_get_max_threads(), pi * h, std::abs(pi * h - M_PI));
    MPI_Finalize();
}
output
2 ranks x 2 threads: pi = 3.141592653590 (error 1.1e-13)

MPI_Init_thread declares how threads will use MPI: FUNNELED (only the main thread calls MPI, the usual choice), SERIALIZED, or MULTIPLE. Typical layouts on a 2-socket, 64-core node: 2 ranks × 32 threads, or 8 × 8, chosen by measurement. On a PBS cluster: #PBS -l select=4:ncpus=64:mpiprocs=8:ompthreads=8; on Slurm: --ntasks-per-node=8 --cpus-per-task=8, with OMP_NUM_THREADS=$SLURM_CPUS_PER_TASK.

B.7 The same in Fortran and Python

Fortran with the modern, type-checked mpi_f08 module and OpenMP (each rank and thread gets its own random stream):

mpi_omp.f90
! mpi_omp.f90 -- hybrid MPI (mpi_f08, the modern Fortran binding) + OpenMP: a Monte Carlo estimate of pi.
! Build: mpif90 -O2 -fopenmp mpi_omp.f90 -o mpi_omp      Run: OMP_NUM_THREADS=2 mpirun -np 2 ./mpi_omp
program mpi_omp
  use mpi_f08
  use omp_lib
  use, intrinsic :: iso_fortran_env, only: dp => real64, i8 => int64
  implicit none
  integer :: rank, nranks, provided
  integer(i8) :: i, hits_local, hits, n_local
  integer(i8), parameter :: n_total = 80000000_i8
  real(dp) :: x, y
  integer :: seed_size, tid
  integer, allocatable :: seed(:)

  call MPI_Init_thread(MPI_THREAD_FUNNELED, provided)
  call MPI_Comm_rank(MPI_COMM_WORLD, rank)
  call MPI_Comm_size(MPI_COMM_WORLD, nranks)
  n_local = n_total / nranks
  hits_local = 0

  !$omp parallel private(x, y, i, seed, seed_size, tid) reduction(+:hits_local)
  tid = omp_get_thread_num()
  call random_seed(size=seed_size)
  allocate(seed(seed_size))
  seed = 12345 + 1000 * rank + 17 * tid          ! a different random stream per rank and thread
  call random_seed(put=seed)
  !$omp do
  do i = 1, n_local
     call random_number(x); call random_number(y)
     if (x*x + y*y <= 1.0_dp) hits_local = hits_local + 1
  end do
  !$omp end do
  !$omp end parallel

  call MPI_Reduce(hits_local, hits, 1, MPI_INTEGER8, MPI_SUM, 0, MPI_COMM_WORLD)
  if (rank == 0) print '(i0, a, i0, a, f10.6)', nranks, ' ranks x ', omp_get_max_threads(), &
       ' threads: pi ~ ', 4.0_dp * real(hits, dp) / real(n_local * nranks, dp)
  call MPI_Finalize()
end program mpi_omp
output
2 ranks x 2 threads: pi ~   3.141627

Python with mpi4py: the halo exchange of B.5, using a Cartesian topology and NumPy buffers. Lower-case methods (allreduce) send any Python object; upper-case ones (Sendrecv) send buffers at C speed:

mpi4py_halo.py
"""mpi4py: the same halo exchange in Python, sending NumPy arrays without copying.
Run: mpiexec -n 4 python mpi4py_halo.py"""
import numpy as np
from mpi4py import MPI

comm = MPI.COMM_WORLD
rank, size = comm.Get_rank(), comm.Get_size()
cart = comm.Create_cart(dims=[size], periods=[True])     # a periodic 1D process topology
left, right = cart.Shift(0, 1)                            # neighbour ranks

N = 4000; n = N // size
dx, kappa = 1.0 / N, 1e-3
dt = 0.4 * dx * dx / kappa
x = (rank * n + np.arange(1, n + 1) - 0.5) * dx - 0.5
u = np.zeros(n + 2); u[1:-1] = np.exp(-0.5 * (x / 0.05) ** 2)

q0 = cart.allreduce(u[1:-1].sum() * dx, op=MPI.SUM)      # lower-case methods: any Python object
for step in range(20000):
    cart.Sendrecv(u[n:n + 1], dest=right, recvbuf=u[0:1], source=left)     # upper-case: buffers, fast
    cart.Sendrecv(u[1:2], dest=left, recvbuf=u[n + 1:n + 2], source=right)
    u[1:-1] += kappa * dt / dx**2 * (u[:-2] - 2 * u[1:-1] + u[2:])
q1 = cart.allreduce(u[1:-1].sum() * dx, op=MPI.SUM)
peak = cart.reduce(u[1:-1].max(), op=MPI.MAX, root=0)
if rank == 0:
    print(f"ranks {size}: heat conserved to {abs(q1 - q0) / q0:.1e}, peak {peak:.5f}")
output
ranks 4: heat conserved to 4.4e-16, peak 0.84515

It gives exactly the C++ answer. Install mpi4py together with its MPI library so the two match (conda install -c conda-forge mpi4py mpich, or pip install mpi4py against the cluster's MPI module).

B.9 Standards and recent directions

  • OpenMP: 4.0/4.5 (2013/2015) added GPU offload and tasks with dependencies; 5.x (2018–2021) improved offload and memory management; 6.0 (November 2024) added easier task programming, loop transformations (fusion, interchange), workdistribute for Fortran array syntax on devices, and full support for C23, C++23 and Fortran 2023.
  • MPI: MPI-3 (2012) added non-blocking collectives and better one-sided communication and the mpi_f08 Fortran module; MPI-4.0/4.1 (2021/2023) added large counts (more than 231 elements), persistent collectives and sessions; MPI-5.0 (2025) defines a standard ABI, so a program compiled with one MPI library can run with another.
  • Directions: one MPI rank per GPU with GPU-aware MPI or NCCL; task-based runtimes for irregular, adaptive problems; directive-based GPU offload for legacy Fortran; and convergence with AI tooling (the same collectives power large-model training).

A container packages a program together with everything it needs to run: a small Linux operating system, compilers, libraries, Python packages and the code itself. Four files in one folder: the modern C++ program from Chapter 9, the Fortran diffusion solver from Chapter 13, a short Python check, and a script that runs all three.

 && apt-get install -y --no-install-recommends g++ gfortran python3 python3-numpy \
 && rm -rf /var/lib/apt/lists/*

D.7 On HPC clusters: Apptainer

Shared clusters do not allow Docker, because it needs administrator rights. They provide Apptainer (formerly Singularity), which runs the same images as an ordinary user:

apptainer pull science-demo.sif docker://ghcr.io/USER/science-demo:1.0   # convert a pushed Docker image
apptainer run science-demo.sif                                          # runs its CMD
apptainer exec --nv science-demo.sif python3 train.py                   # --nv: use the node's NVIDIA GPUs
mpirun -np 64 apptainer exec science-demo.sif ./my_mpi_program          # MPI: the host's MPI launches the containers

For MPI across nodes, the MPI library inside the container should be compatible with the cluster's (same family and a similar version); the MPI-5.0 standard ABI (Appendix B) is designed to make this easier. With Docker on a GPU workstation, use the NVIDIA Container Toolkit and docker run --gpus all ….

D.8 Good practice

  • Small images: slim base images, --no-install-recommends, delete package lists in the same RUN step, and multi-stage builds (compile in one stage, copy only the binaries into a minimal final stage).
  • Reproducibility: pin the base image (ubuntu:24.04, never just latest) and, for published results, package versions (the hadolint linter flags unpinned apt-get install lines, as in this example).
  • A .dockerignore file keeps data, build outputs and .git out of the image.
  • Never put passwords or keys in an image; pass them at run time.
  • Run as a non-root user in production images (USER app).
  • Automate: a GitHub Actions workflow (Appendix A) can build the image and push it to ghcr.io on every release, and VS Code Dev Containers let a whole team develop inside the same image.
