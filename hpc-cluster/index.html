HPC on Imperial CX3: CPU & GPU

High-performance computing — a worked walkthrough on Imperial CX3

Running jobs on an HPC cluster
CPU (MPI) and GPU (JAX), end to end

This deck follows two real jobs submitted to Imperial’s CX3 cluster on 26 Sep 2026: a Monte-Carlo estimate of π parallelised across CPU cores with MPI, and a batched grid calculation offloaded to a single NVIDIA L40S GPU with JAX. Same cluster, two kinds of parallelism — from logging in and building an environment to submitting through the PBS scheduler and reading the result. Every number quoted is from an actual run.

The CPU job (MPI)

400 million random darts split across 4 CPU cores with mpi4py. Result: π = 3.14153 in 3.1 s — distributed-memory parallelism, the classic Fortran-90 + MPI model.

The GPU job (JAX)

A 240×240 grid search on an L40S GPU: 113× faster than the same NumPy code on the CPU, and bit-for-bit the same answer.

What HPC gives you

Many CPU cores across many nodes, big memory, and accelerators (GPUs) — shared through a scheduler that queues everyone’s jobs fairly. You describe the resources you need; it finds a machine.

CPU or GPU?

CPUs (via MPI) for general, branchy, distributed work; GPUs for dense, batched, data-parallel arithmetic. This deck shows exactly when each wins — on real benchmarks.

The shape of a cluster, and getting on it

An HPC cluster is many compute nodes (each a multi-core machine, some with GPUs) plus shared storage, fronted by a login node. You edit files and submit jobs on the login node; the heavy work runs on compute nodes, allocated by the scheduler. Never run big computations on the login node — it is shared by everyone.

Connect (from your own machine)

CX3’s login node is only reachable from the Imperial network, so off-campus the VPN must be up. Check the tunnel before blaming ssh:

# Is the VPN client running, and is the SSH port reachable through it?
pgrep -il zscaler
nc -vz -G 5 login.cx3.hpc.imperial.ac.uk 22
# -> "... port 22 [tcp/ssh] succeeded!"  means the tunnel is good

ssh dmunshi@login.cx3.hpc.imperial.ac.uk
# college password; nothing shows as you type -- that is normal
Diagnose bottom-up. If nc cannot reach port 22, no password will help — the problem is the network, not the login. Fixing connectivity first saves a lot of confusion.

Login node vs compute node

You land on a prompt like [dmunshi@login-bi ~]$. That machine is for editing and submitting only. To compute, you hand a batch job to the scheduler, which runs it on a fresh compute node — a different machine, so your environment must be rebuilt inside the job (next pages).

The job scheduler: how work gets run

A scheduler queues everyone’s jobs and runs each when the resources it asked for are free. CX3 uses PBS (some clusters use Slurm — different commands, same idea). Check which you have rather than guess:

which qsub    # -> /opt/pbs/bin/qsub   => this cluster uses PBS
which sbatch  # -> (nothing)           => no Slurm here

The three commands you need

qsub — submit

qsub run.pbs hands a batch script to the queue and prints a job ID (e.g. 4173401). The job runs when a matching node frees up.

qstat — monitor

qstat -u $USER lists your jobs. The S column: Q queued, R running, then it vanishes when done. qdel <id> cancels one.

The batch script and its #PBS directives

A job is a shell script whose #PBS comment lines request resources. The scheduler reads them; the shell ignores them.

#PBS -N mpi_pi                    # job name (shown in qstat)
#PBS -l select=1:ncpus=4:mem=8gb # 1 node, 4 CPU cores, 8 GB RAM
#PBS -l walltime=00:10:00        # kill it after 10 min if it hangs
#PBS -j oe                       # merge stdout + stderr into one file

You ask for exactly what you need: too little and the job is killed (out of memory / walltime); too much and it waits longer in the queue and wastes the allocation. Output lands in <name>.o<jobid> in the submit directory.

The mental model. A batch script is a note to the scheduler: “give me this much hardware for this long, then run these commands on it.” Everything else is detail.

Software on the node: modules and conda

A compute node starts bare. Clusters expose software through modules; for Python, the modern route is a personal Miniforge + conda environments you build once and reuse. On CX3 the miniforge/3 module hands you an installer:

module load miniforge/3      # puts the miniforge-setup helper on PATH
miniforge-setup              # installs Miniforge into ~/miniforge3
source ~/miniforge3/etc/profile.d/conda.sh   # turn on 'conda'

Two environments — one per job

CPU / MPI env

conda create -y -n mpi \
  python=3.11 numpy mpi4py mpich
conda activate mpi

Installs mpi4py with its own MPICH, so the launcher matches the library.

GPU / JAX env

conda create -y -n gpujax python=3.11 numpy
conda activate gpujax
pip install "jax[cuda12]"

The jax[cuda12] wheels bundle CUDA — no separate CUDA module to load.

The subtle MPI trap. If mpi4py is built against one MPI but you launch with a different mpiexec, every rank thinks it is “rank 0 of 1” and they never cooperate. Installing mpi4py and mpich together in the same env — and activating it so its own mpiexec is first on PATH — keeps them paired. This is the single most common MPI setup failure.

Coming back later you do not reinstall — a fresh session just needs source ~/miniforge3/etc/profile.d/conda.sh then conda activate <name>.

The CPU job: Monte-Carlo π with MPI

The Message Passing Interface is the standard for distributed-memory parallelism: several independent processes (‘ranks’), each with its own memory, cooperating by passing messages. It is the model behind decades of Fortran-90 + MPI scientific codes, and it scales from a few cores to hundreds of thousands across many nodes.

Monte-Carlo π is the ideal first example because it is embarrassingly parallel: throw random darts at a unit square; the fraction inside the quarter circle → π/4. Every dart is independent, so N ranks each throw 1/N of them and the counts are summed at the end.

from mpi4py import MPI
comm = MPI.COMM_WORLD
rank = comm.Get_rank()          # this process's ID: 0,1,2,3
size = comm.Get_size()          # how many processes in total

n_local = TOTAL // size         # each rank's share of the darts
rng = np.random.default_rng(rank)   # independent stream per rank
# ... throw n_local darts, count how many land inside ...

inside_total = comm.reduce(inside_local, op=MPI.SUM, root=0)  # sum onto rank 0
if rank == 0:
    pi_est = 4.0 * inside_total / TOTAL

Two MPI ideas do all the work here: COMM_WORLD (the group of all ranks, each knowing its own rank and the total size), and comm.reduce(…, MPI.SUM, root=0), which takes each rank’s local count, adds them, and leaves the total on rank 0 — which then prints. Seeding each rank with its own number guarantees independent dart streams, so the extra cores do new work rather than repeating each other.

Why this pattern matters. “Split the work, compute locally, reduce the results” is the backbone of MPI — from summing dart counts to global sums in a fluid solver or a cosmological simulation.

Run it: script, submit, result

The batch script requests 4 cores, rebuilds the mpi environment on the node, and launches 4 ranks with mpiexec:

#PBS -N mpi_pi
#PBS -l select=1:ncpus=4:mem=8gb
#PBS -l walltime=00:10:00
#PBS -j oe

cd $PBS_O_WORKDIR                              # run from the submit dir
source ~/miniforge3/etc/profile.d/conda.sh
conda activate mpi
mpiexec -n 4 python mpi_pi.py                  # 4 ranks, one per core

Smoke test, then submit

# cheap check that the ranks really talk, before queuing:
mpiexec -n 4 python -c "from mpi4py import MPI; c=MPI.COMM_WORLD; \
  print('rank', c.Get_rank(), 'of', c.Get_size())"
# -> rank 0 of 4 / 1 of 4 / 2 of 4 / 3 of 4  (any order)

qsub run_pi.pbs        # -> 4173401.pbs-7   (job ID; queue v1_small)
qstat -u $USER         # R = running; gone = finished
cat mpi_pi.o4173401    # read the merged output

The actual result (job 4173401)

ranks               : 4
total samples       : 400,000,000
pi estimate         : 3.14153004       # true pi = 3.14159265...
error vs numpy.pi   : 6.26e-05
wall time (max rank): 3.10 s

400 million darts across 4 cores gave π to ~4 decimal places in about 3 seconds. (One quirk: the PBS footer may report CPU Time: 00:00:00 — an accounting artefact where PBS tallies only the launcher, not the worker ranks. The wall time and correct answer are the real evidence.)

How well does it scale?

Strong scaling asks: fix the problem, add cores — how much faster? For embarrassingly-parallel work like Monte-Carlo π, nearly ideally: doubling the cores nearly halves the time. But most real codes have a serial fraction f that cannot be parallelised, and that caps the speed-up — Amdahl’s law:

S(P) = 1 / ( f + (1 − f)/P )  →   1/f  as P → ∞

Speed-up vs cores for several serial fractions f. Even 5% serial work caps you near 20× no matter how many cores. The star is a measured run: Monte-Carlo π is f≈0, so 2 cores gave a near-ideal 1.95×.

The lesson: throwing more cores at a job only helps up to the point the serial part dominates. A code that is 20% serial can never beat 5×, even on a thousand cores. This is why reducing the serial fraction — not just requesting more ncpus — is the real work of parallel performance. (Weak scaling is the kinder cousin: grow the problem with the cores, and near-linear scaling is often achievable far longer.)

Practical rule. Measure the speed-up as you double cores. When it stops roughly doubling, you have hit your serial fraction — asking for more cores past that point just wastes the allocation and queues longer.

The GPU job: a batched grid on an L40S

A GPU is thousands of small arithmetic units built for doing the same operation on huge arrays at once — data-parallel, not task-parallel. It shines on dense, regular, branch-free numerical work. The example fits a damped oscillator A e−γtcos(ωt) by scoring a 240×240 grid of (A,γ) guesses against noisy data — a dense batched calculation, exactly a GPU’s strength.

import jax, jax.numpy as jnp
DEV = jax.devices()[0]              # the GPU on a GPU node

@jax.jit                           # compile once, then runs on the GPU
def grid(As, Gs, t, y):
    model = As[:,None,None]*jnp.exp(-Gs[None,:,None]*t)*jnp.cos(W0*t)
    r = y - model
    return -0.5*jnp.sum(r*r, axis=2)/SIG**2      # log-likelihood grid

grid(*args).block_until_ready()    # warm-up compile (not timed)

Same code, either device

This is device-agnostic JAX: jax.devices()[0] is a GPU on a GPU node and a CPU otherwise. The identical program runs on your laptop and on the L40S — the job script chooses the hardware, not the Python.

Compile once, run fast

@jax.jit compiles the function to a GPU kernel on first call (a one-time cost, excluded from timing with a warm-up), after which every call is fast.

Not MPI. There is no mpiexec here — one process drives one GPU. GPU parallelism lives inside the array operations, handled by JAX/CUDA, not across ranks.

Run it on a GPU node

The only important change from the CPU script is the resource line: ngpus=1 routes the job to a GPU node (the v1_gpu72 queue). No mpiexec — JAX finds the GPU itself.

#PBS -N gpu_jax
#PBS -l select=1:ncpus=4:mem=24gb:ngpus=1   # <-- ngpus=1 requests one GPU
#PBS -l walltime=00:10:00
#PBS -j oe

cd $PBS_O_WORKDIR
source ~/miniforge3/etc/profile.d/conda.sh
conda activate gpujax                        # the GPU JAX env (not mpi)
python gpu_jax.py                            # no mpiexec

The default GPU on CX3 is an L40S (48 GB); pin a type with :gpu_type=L40S (also RTX6000, A100), and request up to 8 with ngpus= — but only if the code uses them.

The actual result (job 4173425)

JAX backend / device : GPU (cuda:0)      # a real L40S, not the CPU
grid 240x240 x 1500 samples
CPU  (NumPy) :   371.0 ms
JAX  (gpu )  :     3.3 ms   -> x113.4  # 113x faster than NumPy
MAP estimate  A=1.018  gamma=0.257        # truth: 1.00, 0.25
results match: True                       # GPU answer == CPU answer

The GPU did the identical grid search 113× faster and returned the same, correct answer. On the login node the same env reports a CPU device — the GPU only appears inside the job.

Choosing the right processor

Neither is universally faster — they suit different work. Here are both real benchmarks side by side: the dense grid job (left) and satrfi’s RFI acquisition sweep at growing problem size (right).

Left: the 240×240×1500 grid — GPU 113× faster than NumPy. Right: satrfi’s matched-filter acquisition — GPU time stays flat while CPU grows linearly with the template bank, so the speed-up climbs from 7× to 33×.

GPU wins when…

the work is dense, batched and regular — big array maths, grid searches, matrix multiplies, neural nets, HMC/SBI. The more data-parallel arithmetic per byte moved, the bigger the win. Note the GPU line stays nearly flat as the bank grows: headroom to spare.

CPU / MPI wins when…

the work is branchy, latency-bound, or distributed across nodes — complex control flow, large simulations spread over many nodes, or anything that does not vectorise. MPI scales to far more total memory than one GPU holds.

Rule of thumb. If your inner loop is the same arithmetic over a big array, reach for the GPU. If it is many communicating processes or irregular work, reach for CPU + MPI. And the GPU’s edge grows with problem size — small jobs may not repay the data transfer and compile.

The payoff: a genuine end-to-end run, CPU and GPU

The point of all this is real science. The satrfi satellite-RFI pipeline — a differentiable JAX forward model — runs the whole inference arc on the real rfi_faint_16a100 scene: detect a faint injected source (a matched-filter acquisition sweep), localize it (a fine zoom around the peak), and quantify the uncertainty (a Fisher error ellipse) — the identical code run once on a GPU node and once on a CPU node.

The real run on an L40S: left, the acquisition power surface over the full ±6σ search with the acquired point on the true source; right, fine localization with 1σ and 2σ Fisher ellipses on the recovered position.

deviceacquirerecovered θ1σ error|θ̂−θtrue|
GPU (L40S)11.0 s[1.22, −0.64][0.069, 0.05]0.045 σF
CPU (8-core)30.1 s[1.22, −0.64][0.069, 0.05]0.045 σF

Both devices recover the true source (θ = [1.2, −0.6]) to 0.045 coherence widths, well inside the 1σ ellipse — and give bit-for-bit identical numbers. The GPU is 2.7× faster on this single acquisition (the ratio grows when the model is called repeatedly, as in HMC/SBI, or the bank is enlarged).

Portability is the real result. Same θ̂, same error bars on both processors: the device-agnostic JAX code gives identical science on either machine, chosen by the job script alone — the strongest evidence that the pipeline runs anywhere, not just where it was written.

Habits that save time

Storage

Home is small and backed up; use fast scratch ($EPHEMERAL on CX3) for big intermediate data, and copy results back. Don’t compute against your home quota.

Right-size the request

Ask for the cores, memory and walltime you actually need. Over-asking queues longer and wastes the allocation; under-asking gets the job killed. Measure, then request.

Test small, then scale

A login-node smoke test (a few seconds, tiny size) catches the “rank 0 of 1” MPI trap and import errors before you wait in a queue. Then submit the full job.

Rebuild the env in the job

The compute node is a fresh machine — the login-node setup does not carry over. Always source conda.sh and conda activate inside the batch script.

One-page cheat-sheet

# CPU / MPI job
source ~/miniforge3/etc/profile.d/conda.sh
conda activate mpi
cd ~/mpi_pi && qsub run_pi.pbs
qstat -u $USER
cat ~/mpi_pi/mpi_pi.o<jobid>       # -> pi estimate

# GPU / JAX job
source ~/miniforge3/etc/profile.d/conda.sh
conda activate gpujax
cd ~/gpu_jax && qsub run_gpu.pbs
qstat -u $USER                     # Queue = v1_gpu72
cat ~/gpu_jax/gpu_jax.o<jobid>      # -> GPU speed-up
The workflow in one line. Connect → build the env once → write a small batch script that requests hardware and rebuilds the env → qsub, qstat, read .o<jobid>. Everything else is which resources you ask for.
